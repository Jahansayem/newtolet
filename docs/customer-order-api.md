# NewTolet Customer Orders API

REST API the AI inbox agents and admin tools use to create and manage house-search orders. The admin dashboard ("Customer Orders") reads and writes the same records.

| | |
|---|---|
| Base URL | `https://www.newtolet.com/api/v1` |
| Direct URL (no nginx) | `https://api.newtolet.com/functions/v1/customer-orders` |
| Auth | `Authorization: Bearer <API_KEY>` |
| Content type | `application/json` |
| Rate limit | 120 requests per minute per key |

Always use the `www` host. `https://newtolet.com/api/v1/...` redirects to `www`, and a redirected `POST` loses its body.

An order is one paid house-search request (`HOUSE_SEARCH`, 500 BDT) from one customer. A new search is a new order; an old order is never overwritten with new requirements. The paid-ad (50 BDT) order type is not part of this API.

## Endpoints

| Method and path | Purpose | Agent key |
|---|---|---|
| `POST /orders` | Create an order | Yes |
| `GET /orders` | List / search orders | Yes |
| `GET /orders/by-customer?phone=01XXXXXXXXX` | A customer's orders by phone | Yes |
| `GET /orders/{id}` | One order with payment claims, matches and timeline | Yes |
| `PATCH /orders/{id}` | Update customer / requirement fields, assignee, follow-up | Yes |
| `POST /orders/{id}/status` | Change status | Yes |
| `POST /orders/{id}/payment-claim` | Record a payment or partial payment | Yes |
| `POST /orders/{id}/payment-verify` | Verify or reject a payment claim | **Admin only** |
| `POST /orders/{id}/notes` | Add an internal note | Yes |
| `POST /orders/{id}/matches` | Attach a property preview | Yes |
| `GET /orders/{id}/timeline` | Status history, notes and activity | Yes |
| `DELETE /orders/{id}` | Soft delete | **Admin only** |

`{id}` is the order number, for example `NT-2026-0001`.

## Keys and scopes

Two key lists live in the functions environment on the server, each as `label:key,label:key`:

- `ORDERS_AGENT_API_KEYS` — scope `agent`: everything except verifying payments and deleting orders. An agent key also cannot set `REFUNDED` or reopen a closed order.
- `ORDERS_ADMIN_API_KEYS` — scope `admin`: everything.

The label (for example `agent-1`) is recorded as the actor on every write, so the timeline and the audit trail show which key did what. Keys are generated by `scripts/deploy/edge-functions.sh` and stored on the server in `/root/orders-api-keys.txt`; they are never printed or committed.

## Responses

```json
{ "success": true, "data": { } }
{ "success": true, "data": [ ], "meta": { "page": 1, "per_page": 20, "total": 42, "total_pages": 3 } }
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": ["..."] } }
```

Dates are `YYYY-MM-DD`; timestamps are ISO 8601 with a timezone.

### The order object

Every order in every response carries the derived payment and listings fields, so callers never compute them.

```json
{
  "id": "NT-2026-0001",
  "type": "HOUSE_SEARCH",
  "status": "SEARCHING_BY_AI",
  "search": { "mode": "AI", "taken_over_by": null },
  "created_via": "ai_agent",
  "created_by": "agent-1",
  "source": "messenger",
  "customer": { "name": "Rahim Uddin", "phone": "01712345678", "facebook_name": "Rahim Uddin", "facebook_thread_url": "https://www.facebook.com/messages/t/123" },
  "requirements": {
    "area": "Mirpur 10, Kazipara", "rooms": 2, "budget_min": 10000, "budget_max": 15000, "move_in_date": "2026-12-01",
    "family_or_bachelor": "family", "gas": "line", "bathrooms": 1, "balconies": 1, "facilities": "lift preferred", "notes": "Near metro station if possible"
  },
  "service_charge_bdt": 500,
  "payment_status": "PARTIAL_PAID",
  "amount_paid": 200,
  "amount_due": 300,
  "overpaid": false,
  "payment_verification": "CLAIMED",
  "listings_found_count": 2,
  "listings_verified_count": 1,
  "listings_unverified_count": 1,
  "owner_contact_unlocked": false,
  "assigned_to": { "id": "…uuid…", "name": "Staff Name" },
  "follow_up_at": null,
  "payment_claimed_at": "2026-11-16T10:02:11+00:00",
  "payment_verified_at": null,
  "created_at": "2026-11-16T09:40:00+00:00",
  "updated_at": "2026-11-16T10:02:11+00:00"
}
```

- `created_via`: `customer` (placed on the website), `ai_agent` (agent key), `human_agent` (dashboard or admin key).
- `search.mode`: who searched last, `AI` or `HUMAN`. It stays set after the status moves on.
- `payment_status`: `PENDING` (nothing paid) → `PARTIAL_PAID` → `PAID`. Derived from the recorded claims; it cannot be set.
- `amount_paid`: sum of all claims that are not rejected. `amount_due`: charge minus amount paid, never below 0. `overpaid`: more was claimed than the charge.
- `payment_verification`: `UNVERIFIED` → `CLAIMED` (a claim was recorded) → `VERIFIED` (verified claims cover the full charge).
- `listings_found_count` and its verified / unverified split come from the matches attached to the order. They cannot be typed in.
- `owner_contact_unlocked`: true only when the full charge is paid **and** verified and the order is not being refunded or cancelled.

## Statuses

Main flow (search and previews happen before payment):

```
PENDING → REQUIREMENTS_COLLECTED → SEARCHING_BY_AI ⇄ SEARCHING_BY_HUMAN → PREVIEWS_SENT
        → PAYMENT_INTERESTED → PAYMENT_CLAIMED → PAYMENT_VERIFIED → MATCHED → COMPLETED
```

Side paths: `SELF_SERVICE`, `CANCELLED`, `PAYMENT_ISSUE`, `PAYMENT_FAILED`, `REFUND_REQUESTED → REFUNDED`.

Rules enforced by the server:

- `PAYMENT_CLAIMED`, `PAYMENT_VERIFIED` and `PAYMENT_FAILED` can never be set through `POST /status`. A payment claim sets `PAYMENT_CLAIMED`; verifying claims that cover the full charge sets `PAYMENT_VERIFIED`; rejecting the only open claim sets `PAYMENT_FAILED`.
- `SEARCHING_BY_HUMAN` needs `taken_over_by` (who took over the search).
- Search may continue after payment: `PAYMENT_VERIFIED → SEARCHING_BY_AI / SEARCHING_BY_HUMAN / PREVIEWS_SENT`.
- `MATCHED` needs the full charge paid and verified. `REFUND_REQUESTED` needs at least one verified payment.
- An order with a verified payment cannot be `CANCELLED` or moved to `SELF_SERVICE`; use `REFUND_REQUESTED`.
- `COMPLETED` and `REFUNDED` are final. `CANCELLED` and `SELF_SERVICE` can be reopened to `PENDING` by an admin key or the dashboard only. `REFUNDED` can be set by an admin key or the dashboard only.
- Every status change needs a `reason` and is recorded on the timeline with the actor.

Allowed manual moves:

| From | To |
|---|---|
| `PENDING` | `REQUIREMENTS_COLLECTED`, `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `SELF_SERVICE`, `CANCELLED` |
| `REQUIREMENTS_COLLECTED` | `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `PAYMENT_INTERESTED`, `SELF_SERVICE`, `CANCELLED` |
| `SEARCHING_BY_AI` | `SEARCHING_BY_HUMAN`, `PREVIEWS_SENT`, `PAYMENT_INTERESTED`, `SELF_SERVICE`, `CANCELLED`, `REFUND_REQUESTED` |
| `SEARCHING_BY_HUMAN` | `SEARCHING_BY_AI`, `PREVIEWS_SENT`, `PAYMENT_INTERESTED`, `SELF_SERVICE`, `CANCELLED`, `REFUND_REQUESTED` |
| `PREVIEWS_SENT` | `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `PAYMENT_INTERESTED`, `MATCHED`, `SELF_SERVICE`, `CANCELLED`, `REFUND_REQUESTED` |
| `PAYMENT_INTERESTED` | `PAYMENT_ISSUE`, `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `PREVIEWS_SENT`, `SELF_SERVICE`, `CANCELLED` |
| `PAYMENT_CLAIMED` | `PAYMENT_ISSUE`, `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `PREVIEWS_SENT`, `CANCELLED` |
| `PAYMENT_VERIFIED` | `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `PREVIEWS_SENT`, `MATCHED`, `REFUND_REQUESTED` |
| `MATCHED` | `COMPLETED`, `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN`, `REFUND_REQUESTED` |
| `PAYMENT_ISSUE` | `PAYMENT_INTERESTED`, `SELF_SERVICE`, `CANCELLED` |
| `PAYMENT_FAILED` | `PAYMENT_INTERESTED`, `PAYMENT_ISSUE`, `SELF_SERVICE`, `CANCELLED` |
| `REFUND_REQUESTED` | `REFUNDED`, `SEARCHING_BY_AI`, `SEARCHING_BY_HUMAN` (admin only) |
| `CANCELLED`, `SELF_SERVICE` | `PENDING` (admin only) |

## Examples

The examples use these shell variables:

```bash
BASE=https://www.newtolet.com/api/v1
KEY=<agent key>
ADMIN_KEY=<admin key>
```

### Create an order — `POST /orders`

```bash
curl -s -X POST "$BASE/orders" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -H "Idempotency-Key: fb-thread-123-2026-11-16" \
  --data '{
    "type": "HOUSE_SEARCH",
    "customer": { "name": "Rahim Uddin", "phone": "01712345678", "facebook_name": "Rahim Uddin",
                  "facebook_thread_url": "https://www.facebook.com/messages/t/123" },
    "source": "messenger",
    "requirements": { "area": "Mirpur 10, Kazipara", "rooms": 2, "budget_min": 10000, "budget_max": 15000,
                      "move_in_date": "2026-12-01", "family_or_bachelor": "family", "gas": "line",
                      "bathrooms": 1, "balconies": 1, "facilities": "lift preferred",
                      "notes": "Near metro station if possible" },
    "assigned_to": "staff@newtolet.com"
  }'
```

Response `201` with the order: `status: "PENDING"`, `service_charge_bdt: 500`, `payment_status: "PENDING"`, `amount_paid: 0`, `amount_due: 500`, `payment_verification: "UNVERIFIED"`, `listings_found_count: 0`.

- `customer.name` is required, plus at least one of `customer.phone` or `customer.facebook_thread_url`.
- `type` may be omitted; only `HOUSE_SEARCH` is accepted.
- `source`: `messenger` (default for agent keys), `lead_generation`, `manual`, `phone`, `whatsapp`.
- `assigned_to` is optional: an admin user's id or email.
- `follow_up_at` is optional: an ISO 8601 timestamp.
- **Idempotency:** send an `Idempotency-Key` header. Sending the same key again with the same API key returns the original order with `200` instead of creating a duplicate.
- **Duplicate warning:** if an active order already exists for the same phone (or the same Facebook thread when there is no phone) and the same area, the response is `409 DUPLICATE_ORDER_WARNING` with `existing_order_id`. Update that order instead. To create a second one anyway, resend with `"confirm_duplicate": true`.
- The charge is set by the server. Sending `service_charge_bdt`, `amount`, `price`, `payment_status`, a bKash number or any other server-owned field is rejected with `VALIDATION_ERROR`.

### Get one order — `GET /orders/{id}`

```bash
curl -s "$BASE/orders/NT-2026-0001" -H "Authorization: Bearer $KEY"
```

The order object plus `payment_claims`, `matches` and `timeline`.

### List and search — `GET /orders`

```bash
curl -s "$BASE/orders?status=SEARCHING_BY_AI&area=Mirpur&budget_max=15000&rooms=2" -H "Authorization: Bearer $KEY"
curl -s "$BASE/orders?payment_status=PARTIAL_PAID" -H "Authorization: Bearer $KEY"
curl -s "$BASE/orders?has_listings=false&status=PREVIEWS_SENT" -H "Authorization: Bearer $KEY"
curl -s "$BASE/orders?created_via=ai_agent&created_from=2026-11-01&sort=oldest&page=2&per_page=50" -H "Authorization: Bearer $KEY"
```

| Parameter | Meaning |
|---|---|
| `q` | Free text over order number, customer name, phone, Facebook name, area |
| `status` | Repeatable or comma-separated, e.g. `status=SEARCHING_BY_AI&status=PREVIEWS_SENT` |
| `type` | `HOUSE_SEARCH` |
| `phone` | Exact phone (`01XXXXXXXXX` or `+8801XXXXXXXXX`) |
| `area` | Partial match on the requirement area |
| `budget_min`, `budget_max` | Orders whose budget range overlaps the given range |
| `rooms` | Exact number of rooms |
| `move_in_from`, `move_in_to` | Move-in date range, `YYYY-MM-DD` |
| `assigned_to` | Admin user id or email |
| `source` | `messenger`, `lead_generation`, `manual`, `phone`, `whatsapp`, `website` |
| `created_via` | `customer`, `ai_agent`, `human_agent` |
| `payment_status` | `PENDING`, `PARTIAL_PAID`, `PAID` |
| `has_listings` | `true` (at least one listing found) or `false` (none) |
| `listings_found_min` | Only orders with at least N listings found |
| `created_from`, `created_to` | Creation date range, `YYYY-MM-DD` (Dhaka days, inclusive) |
| `sort` | `newest` (default), `oldest`, `move_in` |
| `page`, `per_page` | Pagination; `per_page` defaults to 20, maximum 100 |

An unknown parameter or a bad value is a `VALIDATION_ERROR`; it is never silently ignored. A `PREVIEWS_SENT` order with `has_listings=false` should not exist — treat any result as a data error to fix.

### A customer's orders — `GET /orders/by-customer`

```bash
curl -s "$BASE/orders/by-customer?phone=01712345678" -H "Authorization: Bearer $KEY"
```

### Update — `PATCH /orders/{id}`

```bash
curl -s -X PATCH "$BASE/orders/NT-2026-0001" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "requirements": { "budget_max": 18000, "notes": "Ground floor not acceptable" },
            "customer": { "phone": "01712345678" }, "follow_up_at": "2026-11-18T10:00:00+06:00" }'
```

Send only the fields that change. `null` clears a field. `assigned_to` may be an admin user's id or email, or `null` to unassign. Status, payment fields and the charge cannot be changed here.

### Change status — `POST /orders/{id}/status`

```bash
curl -s -X POST "$BASE/orders/NT-2026-0001/status" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "to_status": "SEARCHING_BY_AI", "reason": "AI search started" }'

curl -s -X POST "$BASE/orders/NT-2026-0001/status" \
  -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  --data '{ "to_status": "SEARCHING_BY_HUMAN", "reason": "Customer asked for a human", "taken_over_by": "Mosiur" }'
```

Response `200` with the updated order, or `422`:

```json
{ "success": false, "error": { "code": "INVALID_TRANSITION", "message": "Cannot move PENDING → PAYMENT_VERIFIED.", "from_status": "PENDING", "to_status": "PAYMENT_VERIFIED" } }
```

### Record a payment — `POST /orders/{id}/payment-claim`

`amount_bdt` is required: the amount the customer actually paid. Send it with either `trx_id` or `sender_last4` — one of the two is enough. A screenshot is not accepted as proof.

```bash
# full payment
curl -s -X POST "$BASE/orders/NT-2026-0001/payment-claim" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "amount_bdt": 500, "trx_id": "9HX7K2M4P1" }'

# partial payment
curl -s -X POST "$BASE/orders/NT-2026-0001/payment-claim" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "amount_bdt": 200, "sender_last4": "3456" }'
```

Response `200`: the order with the new `amount_paid`, `amount_due`, `payment_status`, `payment_verification: "CLAIMED"`, status `PAYMENT_CLAIMED`, plus `claim_id`.

- The endpoint can be called more than once per order; partial payments add up.
- An amount above the charge is accepted and the order is flagged `overpaid: true`.
- The same `trx_id` cannot be recorded twice on one order (`409 CONFLICT`).
- A claim never verifies anything. Verification is a separate human step.
- A payment cannot be recorded on a `COMPLETED`, `REFUNDED`, `CANCELLED`, `SELF_SERVICE` or `REFUND_REQUESTED` order.

### Verify or reject a payment — `POST /orders/{id}/payment-verify` (admin only)

```bash
curl -s -X POST "$BASE/orders/NT-2026-0001/payment-verify" \
  -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  --data '{ "claim_id": "0b9c…", "action": "verify" }'

curl -s -X POST "$BASE/orders/NT-2026-0001/payment-verify" \
  -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  --data '{ "claim_id": "0b9c…", "action": "reject", "note": "TrxID not found in bKash" }'
```

- `claim_id` may be left out when the order has exactly one claim awaiting verification.
- `note` is required when rejecting.
- Verifying does not change any amount. It marks that claim `VERIFIED`. When the verified claims cover the full charge, `payment_verification` becomes `VERIFIED` and the order moves to `PAYMENT_VERIFIED`.
- A verified partial payment does **not** verify the order and does **not** unlock owner contact.
- Rejecting the only open claim of a `PAYMENT_CLAIMED` order moves it to `PAYMENT_FAILED`.
- An agent key gets `403 FORBIDDEN`.

### Add a note — `POST /orders/{id}/notes`

```bash
curl -s -X POST "$BASE/orders/NT-2026-0001/notes" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "note": "Customer asked not to be messaged unless a verified match is found" }'
```

Notes are internal. They are never shown to customers and cannot be edited or deleted.

### Attach a preview — `POST /orders/{id}/matches`

```bash
curl -s -X POST "$BASE/orders/NT-2026-0001/matches" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data '{ "reference_id": "REF-2231", "general_location": "Mirpur 10", "rent": 14000, "verification_status": "unverified" }'
```

- `reference_id` is required and must be unique on the order. It is internal: never tell it to a customer.
- Optional: `property_id` (a NewTolet listing uuid), `owner_contact_phone`, `exact_address`, `owner_permission` (`true` when the owner agreed to share their contact).
- The order's `listings_found_count` and verified / unverified split update from the attached matches.

### Timeline — `GET /orders/{id}/timeline`

```bash
curl -s "$BASE/orders/NT-2026-0001/timeline" -H "Authorization: Bearer $KEY"
```

Newest first. Each entry has `kind` (`status`, `note` or `activity`), `at`, `actor_type` (`admin`, `api_agent`, `api_admin`, `system`) and `actor_label`.

### Soft delete — `DELETE /orders/{id}` (admin only)

```bash
curl -s -X DELETE "$BASE/orders/NT-2026-0001" \
  -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  --data '{ "reason": "Created by mistake" }'
```

The order is hidden from lists and can no longer be changed. Nothing is removed from the database.

## Owner contact

A match's `owner_contact_phone` and `exact_address` are returned only when **both** are true:

1. the order's full charge is paid and verified (`owner_contact_unlocked: true`), and
2. the owner's permission is recorded on that match (`owner_permission: true`).

Otherwise the two fields are absent and `owner_contact_available` is `false`. This applies to every key, including admin keys, and to timeline entries. A partial payment — even a verified one — never unlocks them. The dashboard shows them to staff at all times.

## Errors

| Code | HTTP | When |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Missing or invalid field, unknown field, server-owned field sent, claim without an amount |
| `UNAUTHORIZED` | 401 | Missing or unknown API key |
| `FORBIDDEN` | 403 | Agent key calling payment-verify or delete, or trying a human-only status move |
| `NOT_FOUND` | 404 | Unknown route, order or payment claim |
| `METHOD_NOT_ALLOWED` | 405 | Wrong HTTP method for the route |
| `DUPLICATE_ORDER_WARNING` | 409 | A second active order for the same customer and area (carries `existing_order_id`) |
| `CONFLICT` | 409 | TrxID or reference already recorded, claim already reviewed |
| `INVALID_TRANSITION` | 422 | Status move not allowed |
| `RATE_LIMITED` | 429 | More than 120 requests in a minute (see `Retry-After`) |
| `INTERNAL_ERROR` | 500 | Unexpected failure, or the API keys are not configured |

## What the API never does

- Accept a price, charge, paid total, payment status or payment number from the caller. The only amount it accepts is `amount_bdt` on a payment claim.
- Accept a payment claim without an amount.
- Mark a payment verified from a TrxID or last-4 alone, or treat a partial payment as full payment.
- Return owner phone numbers or exact addresses for an order that is not fully paid, verified and owner-approved.
- Hard-delete an order, or edit or delete timeline entries.
- Create an order without a customer name and at least one contact channel.

## Deployment

1. **Database** — apply `supabase/migrations/20261116090000_customer_orders.sql` (dry run first):

   ```bash
   bash scripts/deploy/supabase-selfhost/run-rls-tests.sh HOST --dry-run-customer-orders
   ssh root@HOST "docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f -" \
     < supabase/migrations/20261116090000_customer_orders.sql
   ```

2. **Function and keys**:

   ```bash
   bash scripts/deploy/edge-functions.sh HOST customer-orders
   # more agent keys: ORDERS_AGENT_KEYS=3 bash scripts/deploy/edge-functions.sh HOST customer-orders
   ```

   The script generates `agent-1` and `admin-1` if they do not exist, writes all keys to `/root/orders-api-keys.txt` on the server, and runs a smoke test (no key → 401, agent list → 200, agent payment-verify → 403).

3. **nginx** — add the `location ^~ /api/v1/` block from `scripts/deploy/nginx-newtolet.conf` to the live `www.newtolet.com` server block, then `nginx -t && systemctl reload nginx`. Until then the API is reachable at the direct URL only.

4. **Test data** — `scripts/deploy/supabase-selfhost/seed-customer-orders.sql` adds three `TEST` orders; `unseed-customer-orders.sql` removes them.

Revert: `scripts/deploy/supabase-selfhost/rollback-customer-orders.sql` (deletes all customer orders; read its header first).
